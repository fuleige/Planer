# 事项规划系统产品与领域设计

> 文档状态：已确认，可作为第一版实现基线  
> 版本：0.2  
> 更新日期：2026-09-22

## 1. 文档目的

本文定义事项规划系统第一版的产品形态、领域模型、时间规则、状态流转、循环任务行为、页面信息架构和验收标准。

本文重点解决以下问题：

- 领域、目标、项目和任务如何组织；
- 无截止日期与父级时间约束如何共存；
- 日、周、月及小数周期如何统一计算；
- 普通任务和循环任务如何完成、取消、逾期；
- 项目和目标如何进入待确认、完成或放弃状态；
- 今日任务、近期任务和总事项安排如何展示；
- PC 与移动端如何使用同一套产品模型。

## 2. 产品定位

系统用于把长期方向、阶段目标、执行项目和具体任务组织在一起，同时提供清晰的今日执行入口和近期风险视图。

产品遵循以下原则：

1. 只有任务可以被直接完成；项目和目标只能在满足条件后由用户确认完成。
2. 上层日期是子级的最晚时间边界，不等同于子任务自己的截止日期。
3. 未完成的循环任务实例必须保留，不能因为进入下一周期而自动消失。
4. “完成”“取消”和“放弃”表达不同结果，统计和状态流转不能混用。
5. 今日页面只承载当前需要行动的任务，不因为事项开始日期到了就自动加入今日列表。
6. 同一套数据在 PC 上强调层级和效率，在移动端强调快速查看与操作。

## 3. 第一版范围

### 3.1 包含范围

- 领域、目标、项目、任务的创建、编辑、排序和删除；
- 目标下的直接任务；
- 普通任务与循环任务；
- 开始日期、周期、截止日期和上层时间约束；
- 今日任务、逾期任务、近期任务和总事项安排；
- 任务完成、取消、重新打开；
- 项目和目标待确认、确认完成、放弃和重新打开；
- 响应式 Web 页面，兼容 PC 和移动端；
- 用户时区和近期范围设置。

### 3.2 首个可用版本

首个可用版本优先实现完整的主流程：

- 领域、目标、项目和任务的基本管理；
- 普通任务，以及每日、每周循环任务；
- 今日、逾期、近期和总事项安排；
- 完成、取消、上层待确认和确认完成；
- 日期换算、上层边界检查和无日期任务筛选；
- PC 与移动端响应式布局；
- 持久化任务数据和基础用户设置。

数据模型为放弃、恢复、批量处理和更多循环规则预留空间，但复杂的整棵层级恢复、批量日期调整等操作可以在主流程稳定后补齐。

### 3.3 暂不包含

- 多人协作、成员权限和任务指派；
- 任务依赖关系和自动排程；
- 工作日、节假日和自定义工作日历；
- 消息推送、邮件提醒和第三方日历同步；
- “每周完成三次”一类配额型循环；
- 工时记录、番茄钟和资源容量管理；
- 目标指标、进度百分比和复杂统计报表。

## 4. 领域层级

系统的标准层级如下：

```text
领域 Area
└── 目标 Goal
    ├── 直接任务 Task
    └── 项目 Project
        └── 项目任务 Task
```

约束如下：

- 目标必须属于一个领域。
- 项目必须属于一个目标。
- 任务必须属于一个目标。
- 任务可以不属于项目；此时它是目标的直接任务。
- 任务属于项目时，该项目必须与任务属于同一个目标。
- 第一版不支持项目嵌套和任务子任务。
- 领域没有完成状态，只负责归类。

### 4.1 领域 Area

领域表示长期存在的责任方向，例如工作、健康、家庭。

领域支持：

- 新增；
- 重命名；
- 排序；
- 归档；
- 删除。

有下级内容的领域不能直接物理删除。用户需要先迁移下级内容，或将整个领域归档。删除在存储层采用软删除，以避免误操作造成不可恢复的数据丢失。

### 4.2 目标 Goal

目标表示希望达成的阶段性结果，例如“完成半程马拉松”。

目标：

- 使用“月”作为周期输入和展示单位；
- 月允许小数；
- 可以没有自身截止日期；
- 可以包含项目和直接任务；
- 不能被直接勾选完成；
- 满足条件后进入待确认状态，由用户确认完成；
- 可以被放弃。

### 4.3 项目 Project

项目表示为达成目标而组织的一组任务，例如“准备上海半马”。

项目：

- 使用“日”或“周”作为周期输入和展示单位；
- 日只能为正整数，周允许小数；
- 可以没有自身截止日期；
- 必须属于一个目标；
- 不能被直接勾选完成；
- 满足条件后进入待确认状态，由用户确认完成；
- 可以被放弃。

### 4.4 任务 Task

任务表示可以直接执行的行动，是唯一可以被用户直接完成的业务实体。

任务：

- 使用“日”或“周”作为周期输入和展示单位；
- 日只能为正整数，周允许小数；
- 必须属于目标，项目可选；
- 可以是普通任务或循环任务；
- 支持完成、取消和重新打开；
- 可以没有自身截止日期；
- 可能因为上层约束而拥有最晚允许日期，但该边界不等于任务自己的截止日期。

循环任务的每一次发生称为“任务实例”。任务实例在产品界面中仍然以任务呈现，不向普通用户暴露内部模型差异。

## 5. 时间模型

### 5.1 基本单位

系统使用自然日，不区分工作日和休息日：

```text
1周 = 7个自然日
1月 = 30个自然日
```

系统同时保留用户输入和归一结果：

```text
duration_value = 用户输入值
duration_unit  = DAY | WEEK | MONTH
duration_days  = ceil(duration_value × 单位对应天数)
```

示例：

| 输入 | 归一结果 |
|---|---:|
| 3日 | 3天 |
| 1周 | 7天 |
| 1.5周 | 11天 |
| 1.5月 | 45天 |
| 1.25月 | 38天 |

当小数换算后不足一个完整自然日时，统一向上取整。界面保留用户输入的原始值，同时明确显示归一结果，例如“1.5 周，按 11 个自然日安排”。

### 5.2 日期范围

开始日期和截止日期都包含在事项周期内：

```text
截止日期 = 开始日期 + duration_days - 1天
duration_days = 截止日期 - 开始日期 + 1天
```

例如，9 月 22 日开始且持续 1 天，截止日期为 9 月 22 日；持续 11 天，截止日期为 10 月 2 日。

所有业务日期使用用户时区下的日历日期，不使用服务器 UTC 日期直接判断“今天”。日期型字段使用 `DATE` 语义，不使用零点时间戳模拟。

### 5.3 默认值

- 新建目标的开始日期默认是今天。
- 新建项目或任务的开始日期默认是今天与上层有效开始日期中的较晚日期。
- 截止日期默认不设置。
- 未设置截止日期时，自身周期为空。
- 如果存在上层截止日期，当前事项可以不设置自身截止日期，但会继承上层时间约束。

### 5.4 三个时间字段的联动

事项编辑界面包含开始日期、周期和截止日期，联动规则如下：

| 用户操作 | 系统行为 |
|---|---|
| 修改开始日期 | 保持周期，重新计算截止日期 |
| 修改周期 | 保持开始日期，重新计算截止日期 |
| 修改自身截止日期 | 保持开始日期，重新计算周期并更新原始输入值 |
| 清除截止日期 | 清除自身周期 |
| 切换展示单位 | 周期天数不变，仅重新计算显示值 |

从日期反算展示值时：

- 项目和任务选择“日”时显示整数天；
- 项目和任务选择“周”时显示 `duration_days / 7`，最多两位小数；
- 目标显示 `duration_days / 30`，最多两位小数。

例如，用户输入 1.5 周后系统归一为 11 天，但仍显示“1.5 周（按 11 个自然日安排）”。只有用户直接修改开始日期和自身截止日期时，才根据 11 天反算并更新显示为 1.57 周。归一结果必须在提交前向用户可见。

### 5.5 自身日期与上层边界

系统区分：

- **自身开始日期**：当前事项设置的开始日期；
- **自身截止日期**：当前事项设置的截止日期，可以为空；
- **最早允许日期**：当前事项及所有上层开始日期中的最晚日期；
- **最晚允许日期**：当前事项及所有上层非空截止日期中的最早日期。

计算规则：

```text
effective_start_limit = max(自身开始日期, 所有上层开始日期)
effective_end_limit   = min(自身及所有上层非空截止日期)
```

上层最晚允许日期是约束，不自动变成普通子任务的自身截止日期。今日和近期列表只把普通任务的自身截止日期当作任务截止日期。若父级今天截止但仍存在没有自身截止日期的未完成任务，今日页面显示父级风险卡，而不是把所有子任务都改成今天截止。

示例：

```text
目标：10月31日截止
└── 项目：未设置自身截止日期
    └── 循环任务：未设置自身结束日期
```

项目和循环任务的最晚允许日期都是 10 月 31 日。界面显示“未单独设置，最晚不得超过目标的 10 月 31 日”。该循环任务不是无限循环；普通任务若没有自身截止日期，仍然属于无日期任务。

### 5.6 父子时间约束

- 子级开始日期不能早于上层最早允许日期。
- 子级自身截止日期不能晚于上层最晚允许日期。
- 子级未设置自身截止日期时，仍归类为无日期任务，不使用上层日期冒充自身截止日期。
- 循环任务未设置结束日期时，使用上层最晚允许日期作为循环边界。
- 上层延后截止日期时，设置了自身截止日期的子级保持不变；受上层约束的循环边界自动跟随。
- 上层提前截止日期且与子级显式日期冲突时，不允许静默保存。
- 上层删除截止日期导致循环任务从有限变为无限时，必须二次确认。

上层日期冲突对话框至少提供：

1. 批量调整冲突子级；
2. 返回并逐项处理；
3. 取消本次修改。

系统不得仅在显示层截断子级日期，而保留互相冲突的持久化数据。

## 6. 循环任务

### 6.1 模型

循环任务由“任务定义”和“任务实例”组成：

```text
循环任务定义
├── 2026-09-22 任务实例
├── 2026-09-23 任务实例
└── 2026-09-24 任务实例
```

用户完成的是某一个任务实例，而不是无限期的循环定义。

### 6.2 第一版循环规则

第一版支持：

- 每 N 天一次；
- 每 N 周一次，并选择星期几；
- 设置循环开始日期；
- 设置自身循环结束日期；
- 不设置自身循环结束日期。

第一版不支持“每周任选三次”一类配额型规则。

### 6.3 有限与无限循环

循环任务的最晚允许日期取以下日期中的最早值：

- 循环规则自身结束日期；
- 所属项目最晚允许日期；
- 所属目标最晚允许日期。

只有自身和所有上层都没有截止日期时，循环任务才是无限循环。

无限循环任务会持续阻止所属项目或目标进入待确认完成状态。这是预期行为，不作为异常处理。

### 6.4 任务实例日期

- 实例开始日期等于循环规则命中的日期。
- 实例周期使用循环任务的 `duration_days`。
- 实例截止日期为实例开始日期加周期减一天。
- 只有开始和截止日期都完整落入循环任务允许范围的实例才会生成。
- 同一个循环任务在同一个命中日期只能产生一个实例。

系统不得静默缩短最后一次实例的周期。如果最后一次命中无法完整容纳，则不生成该实例，并提示它因为上层时间边界被排除。如果高频循环与较长周期导致实例重叠，系统允许保存，但在编辑时显示重叠提示。

### 6.5 实例生成策略

系统不得为无限循环一次性生成全部未来实例。

建议采用按需生成：

- 查询今日任务时确保今天的实例存在；
- 查询近期任务时确保近期窗口内的实例存在；
- 每条循环规则记录 `generated_through_date`，查询时从上次生成位置回填到当前窗口结束日期；
- 即使用户或后台任务长时间没有运行，也必须补齐期间所有本应发生的历史实例；
- 后台按日补充即将到来的实例；
- 已经生成且进入逾期的实例永久保留，直到完成、取消或被软删除；
- 使用 `(recurring_task_id, scheduled_date)` 唯一约束保证幂等。

### 6.6 停止与取消

循环任务操作必须明确区分：

- **完成本次**：仅完成当前任务实例；
- **取消本次**：仅取消当前任务实例；
- **停止循环**：设置循环结束日期，不再生成结束日期之后的实例；
- **取消循环任务**：停止未来循环，并取消仍未处理的实例；
- **批量取消逾期实例**：保留历史记录，不计为完成。

停止循环不会自动删除、完成或取消已有逾期实例。批量取消必须展示影响数量并要求二次确认。

## 7. 状态与完成规则

### 7.1 普通任务和任务实例

状态：

```text
PENDING 未完成
COMPLETED 已完成
CANCELLED 已取消
```

允许的流转：

```text
未完成 ──完成──> 已完成
未完成 ──取消──> 已取消
已完成 ──重新打开──> 未完成
已取消 ──重新打开──> 未完成
```

规则：

- 只有已完成计入完成数量、完成率和成果判断。
- 已取消不计入完成数量，但不再阻塞上层完成。
- 完成和取消都必须记录操作时间。
- 重新打开任务时，需要重新检查并可能打开已完成的上层项目和目标。

### 7.2 项目

项目状态：

```text
ACTIVE 进行中
COMPLETED 已完成
ABANDONED 已放弃
```

“待确认完成”是根据任务现状计算出的界面状态 `can_complete`，不是必须持久化的生命周期状态，避免任务变化后产生状态不同步。

项目自动进入待确认完成需要同时满足：

1. 不存在未完成或逾期的普通任务；
2. 不存在未来仍会产生实例的循环任务；
3. 所有已产生的循环任务实例均已完成或取消；
4. 至少有一个普通任务或循环实例实际完成。

项目不能自动完成。用户必须点击“确认完成”。

如果全部任务都被取消，项目不能确认为完成，只能继续补充任务或标记为已放弃。

### 7.3 目标

目标持久化状态与项目相同：

```text
ACTIVE 进行中
COMPLETED 已完成
ABANDONED 已放弃
```

目标的“待确认完成”同样通过 `can_complete` 实时计算。

目标自动进入待确认完成需要同时满足：

1. 所有未放弃的项目都已经确认完成；
2. 所有直接普通任务均已完成或取消；
3. 所有直接循环任务已经结束，不会再产生未来实例；
4. 直接循环任务的已有实例均已完成或取消；
5. 至少存在一个已完成项目、已完成直接任务或已完成循环实例。

目标不能自动完成。用户必须点击“确认完成”。

如果所有项目都已放弃且所有直接任务都已取消，目标不能确认为完成，只能继续补充内容或标记为已放弃。

### 7.4 放弃

放弃表达“该目标或项目不再继续”，不是完成。

- 放弃项目时，必须确认如何处理未完成任务和循环任务；完成放弃操作后不得留下活动任务。
- 放弃目标时，需要同时放弃仍在进行的项目，并取消目标下仍未完成的直接任务。
- 放弃操作必须二次确认。
- 放弃操作应可恢复；恢复后原先自动取消的内容默认仍保持取消，由用户选择需要重新打开的任务。

### 7.5 重新打开与锁定

- 已完成的项目和目标默认锁定结构性修改。
- 在已完成项目中新增任务前，必须先重新打开项目；重新打开项目会同时重新打开已完成目标。
- 重新打开已完成任务或实例时，如果会影响已完成项目或目标，必须先展示影响范围并由用户确认；确认后在同一事务中重新打开任务及上层事项。
- 在已放弃项目或目标中重新打开任务前，必须先恢复对应的上层事项。
- 不允许无提示地改变已经确认完成的项目或目标。

## 8. 页面信息架构

系统包含三个一级入口：

1. 今日任务；
2. 近期任务；
3. 总事项安排。

### 8.1 今日任务

今日页面建议按以下顺序展示：

```text
待确认
边界风险
已逾期
今日截止
今日循环
今日已完成
```

#### 待确认

展示已经满足条件、等待用户确认完成的项目和目标。待确认项目和目标不是任务，不计入今日任务红色角标。

#### 边界风险

当目标或项目今天到达自身截止日期，但仍包含没有自身截止日期的未完成任务时，展示聚合风险卡，例如“目标今天截止，仍有 8 个无日期任务”。这些子任务不会被自动改成今天截止，也不逐条计入今日任务角标。

#### 已逾期

包括：

- 自身截止日期早于今天且仍未完成的普通任务；
- 实例截止日期早于今天且仍未完成的循环任务实例。

循环任务逾期实例不会自动跳过或消失。相同循环任务的多个逾期实例默认聚合显示，例如“每天阅读：逾期 12 次”，用户可以展开处理。

#### 今日截止

展示自身截止日期等于今天且尚未完成的普通任务。

#### 今日循环

展示循环规则在今天命中的任务实例。即使实例周期超过一天，它也在发生当天出现在今日循环中。

同一个实例同时满足“今日循环”和“今日截止”时只展示一次、只计数一次，优先归入“今日循环”。

#### 今日已完成

展示今天完成的任务和任务实例，默认折叠。

普通任务仅仅已经开始、但今天不是截止日期时，不进入今日任务。

### 8.2 今日红色角标

```text
红色角标 = 未完成逾期任务数 + 今日未完成任务数
```

- 已取消任务不计数；
- 同一任务或实例不重复计数；
- 超过 99 显示 `99+`；
- 待确认项目和目标不计入角标。

### 8.3 近期任务

近期范围支持用户选择：

- 7 天；
- 14 天，默认值；
- 30 天；
- 自定义天数。

近期窗口从明天开始，不包含今天：

```text
[明天, 今天 + N天]
```

展示：

- 自身截止日期落在窗口内的未完成普通任务；
- 循环规则在窗口内命中的未来任务实例。

不展示：

- 今日任务；
- 已逾期任务；
- 已完成或已取消任务；
- 项目和目标。

近期页面按日期分组，并允许按领域、目标和项目筛选。普通任务的上层时间边界不作为任务自己的近期截止日期。

### 8.4 近期黄色角标

黄色角标统计近期窗口内尚未完成的普通任务和循环实例，不包含今日及逾期任务。超过 99 显示 `99+`。

### 8.5 总事项安排

总事项安排是事项创建、组织和全局检查入口，以领域分组并呈现完整层级：

```text
健康
└── 完成半程马拉松       3.00月   12月20日
    ├── 购买跑鞋          1日      10月03日
    └── 准备上海半马      2.00周   10月31日
        ├── 选择训练计划   2日      10月05日
        └── 每周一三五跑步 循环     跟随项目
```

每一项至少展示：

- 名称；
- 类型；
- 状态；
- 开始日期；
- 周期；
- 自身截止日期和上层最晚允许日期；
- 循环标识；
- 逾期或时间冲突提示。

总事项安排提供“未安排截止日期”和“长期未更新”筛选，避免普通无日期任务长期沉底。父级最晚允许日期单独显示为边界提示，不冒充任务截止日期。

第一版以层级列表为主，时间轴或甘特图作为后续能力。

## 9. 响应式界面

### 9.1 PC 端

- 左侧固定一级菜单，显示红色和黄色角标；
- 中间为主要任务或层级列表；
- 点击事项后在右侧详情面板查看和编辑；
- 总事项安排支持逐层展开、收起和筛选；
- 批量操作使用列表选择模式。

### 9.2 移动端

- 底部使用三个主导航：今日、近期、总安排；
- 红色和黄色角标显示在对应底部导航上；
- 总事项安排使用可展开卡片，不直接缩放 PC 树形表格；
- 新增和编辑使用全屏表单或底部抽屉；
- 高频操作“完成”和“取消”在单手区域内可触达；
- 批量取消等高风险操作必须进入确认页，不使用容易误触的滑动手势直接执行。

建议在约 768px 宽度切换移动与桌面导航，但最终断点应根据实际组件测试确定。

## 10. 核心交互

### 10.1 新建事项

新建入口根据当前上下文预填所属层级：

- 在领域下新建目标；
- 在目标下新建项目或直接任务；
- 在项目下新建任务；
- 在今日或近期页面新建任务时，必须选择目标，项目可选。

表单应先展示必要字段：名称、所属关系、开始日期、周期或截止日期、是否循环。高级循环规则按需展开。

### 10.2 完成任务

- 普通任务点击完成后立即更新状态；
- 循环任务只完成当前实例；
- 完成最后一个阻塞项后，系统生成项目或目标待确认提示；
- 用户可撤销刚刚的完成操作。

### 10.3 取消任务

- 普通任务取消后保留在历史中；
- 循环实例取消只影响本次；
- 取消不计入完成统计；
- 取消最后一个未处理任务后，如果上层至少有真实完成成果，上层可以进入待确认；
- 如果全部任务都被取消，上层只能放弃，不能确认完成。

### 10.4 确认项目或目标完成

确认对话框展示：

- 实际完成任务数；
- 已取消任务数；
- 开始和完成日期；
- 是否存在尚未解决的警告。

确认成功后锁定结构性修改，并记录确认时间。

### 11.4 TaskDefinition

```text
id
goal_id
project_id nullable
type ONE_TIME | RECURRING
title
description
start_date
own_due_date nullable
duration_value nullable
duration_days nullable
display_unit DAY | WEEK
definition_status ACTIVE | STOPPED | CANCELLED
sort_order
deleted_at
created_at

```

任务定义保存稳定的标题、归属和生成规则，不保存某一次执行的完成状态。普通任务也会生成唯一一个任务实例，因此今日、近期、完成、取消和统计查询不需要拼接两套状态模型。

当 `project_id` 非空时，项目的 `goal_id` 必须等于任务的 `goal_id`。该一致性需要在数据库约束或领域服务中强制保证。

### 11.5 RecurrenceRule

```text
id
task_id unique
frequency DAILY | WEEKLY
interval positive integer
weekdays nullable
own_end_date nullable
generated_through_date nullable
series_status ACTIVE | ENDED | CANCELLED
created_at
updated_at
```

任务的 `start_date` 同时是循环开始日期。循环最晚允许日期由自身结束日期和上层时间边界共同决定。`generated_through_date` 用于在系统中断或用户长期未访问后补齐历史实例。

### 11.6 TaskOccurrence

```text
id
task_id
scheduled_date
due_date nullable
status PENDING | COMPLETED | CANCELLED
completed_at nullable
cancelled_at nullable
created_at
updated_at

unique(task_id, scheduled_date)
```

普通任务只有一个实例，其 `scheduled_date` 使用任务开始日期，`due_date` 使用任务自身截止日期；循环任务拥有多个实例。产品界面仍将实例称为“任务”。

### 11.7 UserPreference

```text
user_id
timezone
upcoming_days default 14
created_at
updated_at
```

## 12. 关键领域服务

实现时应将以下逻辑集中在领域服务中，避免分散到页面组件：

### 12.1 DurationCalculator

- 日、周、月转整数天；
- 保留原始周期值和展示单位；
- 开始日期与周期计算截止日期；
- 开始和截止日期反算周期；
- 格式化周和月的小数展示。

### 12.2 EffectiveDateResolver

- 计算最早和最晚允许日期；
- 检测父子日期冲突；
- 评估修改上层日期的影响范围。

### 12.3 RecurrenceService

- 判断某日是否命中循环规则；
- 幂等生成任务实例；
- 根据生成游标回填遗漏的历史实例；
- 计算循环最晚允许日期；
- 停止或取消循环；
- 聚合逾期实例。

### 12.4 CompletionPolicy

- 判断项目和目标是否满足待确认条件；
- 区分完成、取消和放弃；
- 在任务重新打开时回退上层状态；
- 禁止没有真实完成成果的上层事项确认完成。

### 12.5 TaskQueryService

- 查询今日截止；
- 查询今日循环；
- 查询逾期；
- 查询近期窗口；
- 查询无日期任务和父级边界风险；
- 去重并计算菜单角标。

## 13. 删除与历史数据

- 业务实体默认使用软删除。
- 完成记录和取消记录不能因停止循环而被删除。
- 删除循环任务时必须说明是否仅隐藏定义，还是同时软删除历史实例。
- 第一版建议默认保留历史实例，仅停止未来生成。
- 领域、目标或项目存在下级内容时，删除操作必须展示影响范围。
- 已完成事项优先归档，不建议直接删除。

## 14. 边界情况

### 14.1 没有截止日期

- 事项仍然可以存在于总事项安排。
- 普通任务不会因为开始日期到达而进入今日或近期。
- 循环任务根据循环规则进入今日和近期。
- 上层截止日期只作为最晚允许边界，不自动变成普通任务的自身截止日期。

### 14.2 无限循环任务

- 不批量生成未来所有实例。
- 会阻止所属项目或目标完成。
- 可以通过设置结束日期、停止循环或取消循环任务解除阻塞。

### 14.3 大量循环逾期

- 所有未完成实例仍然保留为逾期。
- 列表按循环定义聚合，避免页面出现数百条重复内容。
- 展开后允许逐条完成、逐条取消或批量取消。
- 批量取消不计为完成。

### 14.4 全部任务取消

- 项目或目标不能确认完成。
- 用户可以新增任务继续执行，或将项目、目标标记为已放弃。

### 14.5 跨时区

- 今日、逾期和循环命中都以用户设置的时区计算。
- 修改时区不会修改日期字段本身，但可能改变当前“今天”的判定。

### 14.6 并发操作

- 完成、取消和确认完成操作应具备幂等性。
- 确认项目或目标完成前必须在服务端重新校验条件。
- 前端显示可确认不代表服务端可以跳过最终校验。

## 15. 第一版验收标准

### 15.1 时间

- [ ] 新建事项开始日期默认为今天或允许的最早日期。
- [ ] 日只允许正整数。
- [ ] 周和月允许小数，换算后向上取整为整数天。
- [ ] 1.5 周归一为 11 天。
- [ ] 归一后仍保留用户输入的 1.5 周，不自动显示成 1.57 周。
- [ ] 1.5 月归一为 45 天。
- [ ] 修改开始日期、周期、截止日期时按既定规则联动。
- [ ] 子级不能保存到父级最早、最晚允许边界之外。
- [ ] 未设置自身截止日期的子级正确继承上层约束。

### 15.2 任务列表

- [ ] 今日页面只展示逾期、今日截止或今日命中的循环任务。
- [ ] 单纯已经开始的普通任务不会进入今日页面。
- [ ] 逾期循环实例不会自动消失。
- [ ] 近期默认展示未来 14 天且不包含今天。
- [ ] 红色和黄色角标不存在重复计数。
- [ ] 已取消任务不计入角标。

### 15.3 循环

- [ ] 无限循环不会预生成无限数据。
- [ ] 系统长时间未运行后，能够根据生成游标补齐遗漏实例。
- [ ] 同一循环任务同一天不会产生重复实例。
- [ ] 上层存在截止日期时，下层循环不会越过最晚允许日期。
- [ ] 停止循环不会删除已有逾期实例。
- [ ] 批量取消展示影响数量并二次确认。

### 15.4 完成状态

- [ ] 只有任务或任务实例可以直接完成。
- [ ] 满足条件的项目和目标进入待确认，而不是自动完成。
- [ ] 无限循环任务阻止上层进入待确认。
- [ ] 已取消任务不阻塞上层，但不计入完成成果。
- [ ] 全部任务取消时，上层不能确认完成。
- [ ] 重新打开任务会正确回退已完成的上层状态。
- [ ] 已完成上层在修改结构前需要重新打开。

### 15.5 响应式体验

- [ ] PC 使用左侧导航，移动端使用底部三项导航。
- [ ] 两种布局均能看到今日红色和近期黄色角标。
- [ ] 移动端总事项安排使用可展开卡片，不出现不可用的横向树表。
- [ ] 完成、取消和查看详情可以在移动端单手完成。
