# 事项规划系统产品与领域设计

> 文档状态：第一版实现基线；2026-09-24 新增的“今日操作与撤回”交互已实现，待用户手工验收。
> 版本：0.6
> 更新日期：2026-09-24

## 1. 文档目的

本文定义事项规划系统第一版的产品形态、领域模型、时间规则、状态流转、循环任务行为、页面信息架构和验收标准。

本文重点解决以下问题：

- 领域、目标、项目和任务如何组织；
- 无截止日期与父级时间约束如何共存；
- 日、周、月及小数周期如何统一计算；
- 普通任务和循环任务如何完成、取消、逾期；
- 项目和目标如何进入待确认、完成或放弃状态；
- 今日任务、近期任务和总事项安排如何展示；
- PC 与移动端如何使用同一套产品模型；
- 公网部署时如何保护页面和数据接口。

## 2. 产品定位

系统用于把长期方向、阶段目标、执行项目和具体任务组织在一起，同时提供清晰的今日执行入口和近期风险视图。

产品遵循以下原则：

1. 只有任务可以被直接完成；项目和目标只能在满足条件后由用户确认完成。
2. 上层日期是子级的最晚时间边界，不等同于子任务自己的截止日期。
3. 未完成的循环任务实例不会因换周期自动消失；每条规则最多保留最近 16 条未处理逾期，超过上限才自动清理最早记录。
4. “完成”“取消”和“放弃”表达不同结果，统计和状态流转不能混用。
5. 今日页面只承载当前需要行动的任务，不因为事项开始日期到了就自动加入今日列表。
6. 同一套数据在 PC 上强调层级和效率，在移动端强调快速查看与操作。

## 3. 第一版范围

### 3.1 包含范围

- 领域、目标、项目、任务的创建、编辑、排序和删除；
- 目标下的直接任务；
- 普通任务与循环任务；
- 开始日期、周期、截止日期和上层时间约束；
- 今日任务、逾期任务、近期任务和总事项安排；
- 任务完成、取消、重新打开；
- 项目和目标待确认、确认完成、放弃和重新打开；
- 响应式 Web 页面，兼容 PC 和移动端；
- 用户时区和近期范围设置。

### 3.2 首个可用版本

首个可用版本优先实现完整的主流程：

- 领域、目标、项目和任务的基本管理；
- 普通任务，以及每日、每周循环任务；
- 今日、逾期、近期和总事项安排；
- 完成、取消、上层待确认和确认完成；
- 日期换算、上层边界检查和无日期任务筛选；
- PC 与移动端响应式布局；
- 持久化任务数据和基础用户设置。

数据模型为放弃、恢复、批量处理和更多循环规则预留空间，但复杂的整棵层级恢复、批量日期调整等操作可以在主流程稳定后补齐。

### 3.3 暂不包含

- 多人协作、成员权限和任务指派；
- 任务依赖关系和自动排程；
- 工作日、节假日和自定义工作日历；
- 消息推送、邮件提醒和第三方日历同步；
- “每周完成三次”一类配额型循环；
- 工时记录、番茄钟和资源容量管理；
- 目标指标、进度百分比和复杂统计报表。

## 4. 领域层级

系统的标准层级如下：

```text
领域 Area
└── 目标 Goal
    ├── 直接任务 Task
    └── 项目 Project
        └── 项目任务 Task
```

约束如下：

- 目标必须属于一个领域。
- 项目必须属于一个目标。
- 任务必须属于一个目标。
- 任务可以不属于项目；此时它是目标的直接任务。
- 任务属于项目时，该项目必须与任务属于同一个目标。
- 第一版不支持项目嵌套和任务子任务。
- 领域没有完成状态，只负责归类。

### 4.1 领域 Area

领域表示长期存在的责任方向，例如工作、健康、家庭。

领域支持：

- 新增；
- 重命名；
- 排序；
- 归档；
- 删除。

新建领域时从协调的预设色板中选择标识色，默认优先推荐尚未使用的颜色。界面显示颜色名称和效果预览；标识色用于侧栏、任务标记与总事项安排，避免让用户直接面对原生颜色取值器。

有下级内容的领域不能直接物理删除。用户需要先迁移下级内容，或将整个领域归档。删除在存储层采用软删除，以避免误操作造成不可恢复的数据丢失。

### 4.2 目标 Goal

目标表示希望达成的阶段性结果，例如“完成半程马拉松”。

目标：

- 使用“月”作为周期输入和展示单位；
- 月允许小数；
- 可以没有自身截止日期；
- 可以包含项目和直接任务；
- 不能被直接勾选完成；
- 满足条件后进入待确认状态，由用户确认完成；
- 可以被放弃。

### 4.3 项目 Project

项目表示为达成目标而组织的一组任务，例如“准备上海半马”。

项目：

- 使用“日”或“周”作为周期输入和展示单位；
- 日只能为正整数，周允许小数；
- 可以没有自身截止日期；
- 必须属于一个目标；
- 不能被直接勾选完成；
- 满足条件后进入待确认状态，由用户确认完成；
- 可以被放弃。

### 4.4 任务 Task

任务表示可以直接执行的行动，是唯一可以被用户直接完成的业务实体。

任务：

- 使用“日”或“周”作为周期输入和展示单位；
- 日只能为正整数，周允许小数；
- 必须属于目标，项目可选；
- 可以是普通任务或循环任务；
- 支持完成、取消和重新打开；
- 可以没有自身截止日期；
- 可能因为上层约束而拥有最晚允许日期，但该边界不等于任务自己的截止日期。

循环任务的每一次发生称为“任务实例”。任务实例在产品界面中仍然以任务呈现，不向普通用户暴露内部模型差异。

## 5. 时间模型

### 5.1 基本单位

系统使用自然日，不区分工作日和休息日：

```text
1周 = 7个自然日
1月 = 30个自然日
```

系统同时保留用户输入和归一结果：

```text
duration_value = 用户输入值
duration_unit  = DAY | WEEK | MONTH
duration_days  = ceil(duration_value × 单位对应天数)
```

示例：

| 输入 | 归一结果 |
|---|---:|
| 3日 | 3天 |
| 1周 | 7天 |
| 1.5周 | 11天 |
| 1.5月 | 45天 |
| 1.25月 | 38天 |

当小数换算后不足一个完整自然日时，统一向上取整。表单可保留用户输入的小数值并明确显示归一结果；事项列表的时间文案只显示整数月、周、天，例如 45 天显示“1月2周1天”。有截止日期且尚未开始时显示完整的“总时间”；开始后改为含今天在内的“剩余”时间，截止当天显示“今天截止”，过期显示“已逾期 X 天”。已完成、已放弃或已取消的事项只显示状态，不再倒计时。

### 5.2 日期范围

开始日期和截止日期都包含在事项周期内：

```text
截止日期 = 开始日期 + duration_days - 1天
duration_days = 截止日期 - 开始日期 + 1天
```

例如，9 月 22 日开始且持续 1 天，截止日期为 9 月 22 日；持续 11 天，截止日期为 10 月 2 日。

所有业务日期使用用户时区下的日历日期，不使用服务器 UTC 日期直接判断“今天”。日期型字段使用 `DATE` 语义，不使用零点时间戳模拟。

### 5.3 默认值

- 新建领域和目标的开始日期默认是今天。
- 新建项目或任务的开始日期默认是今天与上层有效开始日期中的较晚日期。
- 截止日期默认不设置。
- 未设置截止日期时，自身周期为空；开始后显示“已持续 X 天”，尚未开始时显示“尚未开始”。
- 如果存在上层截止日期，当前事项可以不设置自身截止日期，但会继承上层时间约束。

### 5.4 三个时间字段的联动

事项编辑界面包含开始日期、周期和截止日期，联动规则如下：

| 用户操作 | 系统行为 |
|---|---|
| 修改开始日期 | 保持周期，重新计算截止日期 |
| 修改周期 | 保持开始日期，重新计算截止日期 |
| 修改自身截止日期 | 保持开始日期，重新计算周期并更新原始输入值 |
| 清除截止日期 | 清除自身周期 |
| 切换展示单位 | 周期天数不变，仅重新计算显示值 |

从日期反算展示值时：

- 项目和任务选择“日”时显示整数天；
- 项目和任务选择“周”时显示 `duration_days / 7`，最多两位小数；
- 领域和目标的表单以月录入，可保留最多两位小数；列表显示拆分后的整数月、周、天。

例如，用户输入 1.5 周后系统归一为 11 天，但仍显示“1.5 周（按 11 个自然日安排）”。只有用户直接修改开始日期和自身截止日期时，才根据 11 天反算并更新显示为 1.57 周。归一结果必须在提交前向用户可见。

### 5.5 自身日期与上层边界

系统区分：

- **自身开始日期**：当前事项设置的开始日期；
- **自身截止日期**：当前事项设置的截止日期，可以为空；
- **最早允许日期**：当前事项及所有上层开始日期中的最晚日期；
- **最晚允许日期**：当前事项及所有上层非空截止日期中的最早日期。

计算规则：

```text
effective_start_limit = max(自身开始日期, 所有上层开始日期)
effective_end_limit   = min(自身及所有上层非空截止日期)
```

领域也可设置开始与截止日期，并约束所有下级。上层最晚允许日期是约束，不自动变成普通子任务的自身截止日期。今日和近期列表只把普通任务的自身截止日期当作任务截止日期。若父级今天截止但仍存在没有自身截止日期的未完成任务，今日页面显示父级风险卡，而不是把所有子任务都改成今天截止。

示例：

```text
目标：10月31日截止
└── 项目：未设置自身截止日期
    └── 循环任务：未设置自身结束日期
```

项目和循环任务的最晚允许日期都是 10 月 31 日。界面显示“未单独设置，最晚不得超过目标的 10 月 31 日”。该循环任务不是无限循环；普通任务若没有自身截止日期，仍然属于无日期任务。

### 5.6 父子时间约束

- 子级开始日期不能早于上层最早允许日期。
- 子级自身截止日期不能晚于上层最晚允许日期。
- 子级未设置自身截止日期时，仍归类为无日期任务，不使用上层日期冒充自身截止日期。
- 循环任务未设置结束日期时，使用上层最晚允许日期作为循环边界。
- 上层延后截止日期时，设置了自身截止日期的子级保持不变；受上层约束的循环边界自动跟随。
- 上层提前截止日期且与子级显式日期冲突时，不允许静默保存。
- 上层删除截止日期导致循环任务从有限变为无限时，必须二次确认。

上层日期冲突对话框至少提供：

1. 批量调整冲突子级；
2. 返回并逐项处理；
3. 取消本次修改。

系统不得仅在显示层截断子级日期，而保留互相冲突的持久化数据。

当前实现先阻止有冲突的上层日期修改，并提示用户逐项调整；批量调整子级仍是后续增强。移除上层截止日期且会使循环任务变为无限时，需要用户勾选确认。

## 6. 循环任务

### 6.1 模型

循环任务由“任务定义”和“任务实例”组成：

```text
循环任务定义
├── 2026-09-22 任务实例
├── 2026-09-23 任务实例
└── 2026-09-24 任务实例
```

用户完成的是某一个任务实例，而不是无限期的循环定义。

### 6.2 第一版循环规则

第一版支持：

- 每 N 天一次；
- 每 N 周一次：命中的周内每天提醒，直到用户确认“本周完成”；
- 设置循环开始日期；
- 设置自身循环结束日期；
- 不设置自身循环结束日期。

每周以用户时区的周一至周日划分，开始日期所在周是第一个命中周；每 N 周只在命中周提醒，首周从开始日期起计算。旧按周任务的已完成周视为本周已完成，不为其补造其他日期的逾期；未完成周按日补齐历史。

### 6.3 有限与无限循环

循环任务的最晚允许日期取以下日期中的最早值：

- 循环规则自身结束日期；
- 所属项目最晚允许日期；
- 所属目标最晚允许日期。
- 所属领域最晚允许日期。

只有自身和所有上层都没有截止日期时，循环任务才是无限循环。

无限循环任务会持续阻止所属项目或目标进入待确认完成状态。这是预期行为，不作为异常处理。

### 6.4 任务实例日期

- 实例开始日期等于循环规则命中的日期。
- 按日循环实例周期使用循环任务的 `duration_days`，截止日期为开始日期加周期减一天。
- 按周循环在命中周的每天生成一条当日实例，当日未操作则次日逾期；预计时长只作为工作量参考。
- 只有开始和截止日期都完整落入循环任务允许范围的实例才会生成。
- 同一个循环任务在同一个命中日期只能产生一个实例。

系统不得静默缩短最后一次实例的周期。如果最后一次命中无法完整容纳，则不生成该实例，并提示它因为上层时间边界被排除。如果高频循环与较长周期导致实例重叠，系统允许保存，但在编辑时显示重叠提示。

### 6.5 实例生成策略

系统不得为无限循环一次性生成全部未来实例。

建议采用按需生成：

- 查询今日任务时确保今天的实例存在；
- 近期列表不逐条展示循环实例；
- 每条循环规则记录 `generated_through_date`，查询时从上次生成位置回填到今天；
- 即使用户长期没有运行系统，也必须补齐期间本应发生的历史实例；
- 不预生成未来实例；下次打开系统时再生成当天及缺失的历史实例；
- 已经进入逾期的普通任务可重设截止日期或手动删除；循环任务逾期实例只能手动删除本条，每条规则最多保留最近 16 条未处理逾期，超过上限时自动清理最早的一条，并显示自动清理计数；
- 使用 `(recurring_task_id, scheduled_date)` 唯一约束保证幂等。

### 6.6 停止与取消

循环任务操作必须明确区分：

- **今日完成**：仅完成今日实例，按周循环明日继续提醒；
- **今日跳过**：仅取消今日实例，按周循环明日继续提醒；
- **本周完成**：记录一次独立的周级完成成果，关闭本周剩余提醒；不自动把今日实例标为完成、不增加“今日完成”次数，此前逾期仍保留，直到手动清理或达到 16 条上限；
- **停止循环**：暂停生成未来实例，已有逾期仍保留；
- **取消循环任务**：停止生成未来实例，已有逾期仍保留；

逾期实例不再提供补记完成、跳过或重新打开。普通逾期任务可重设截止日期为今天或以后，保持待处理状态；也可手动删除任务。循环逾期实例只能删除本条，不影响后续循环。改期直接覆盖当前截止日期，不增加原定日期或改期历史字段；仍须遵守上层时间边界。除了循环任务超过 16 条上限这一种情况，系统不得自动清理逾期。停止循环不会自动删除、完成或取消已有逾期实例。

当前编辑规则：普通任务可修改名称、备注、归属和时间；循环任务若已有今天或更早的实例（或已处理实例），为保留历史，只允许修改名称和备注。尚无此类实例时，可以重排未来尚未处理的实例。已有任务暂不支持在普通任务和循环任务之间切换类型。

当前“停止循环”会将规则状态设为已停止，撤下尚未发生的待办实例，并保留已发生、已完成或已取消的历史实例；“恢复循环”会沿原规则继续生成未来实例。停止／恢复均需确认。完成上层事项仍须先处理所有保留的待办实例。

“总事项安排”中的任务提供“处理／记录”入口，列出待处理与已处理实例。无截止日期的普通任务可以在这里完成或取消。已处理实例能否撤回，取决于实例截止日期和上层状态；上层已完成时不得自动重新打开。

## 7. 状态与完成规则

### 7.1 普通任务和任务实例

状态：

```text
PENDING 未完成
COMPLETED 已完成
CANCELLED 已取消
```

允许的流转：

```text
未完成 ──完成──> 已完成
未完成 ──取消──> 已取消
已完成 ──重新打开──> 未完成
已取消 ──重新打开──> 未完成
```

规则：

- 只有已完成计入完成数量、完成率和成果判断。
- 已取消不计入完成数量，但不再阻塞上层完成。
- 完成和取消都必须记录操作时间。
- 撤回完成或取消本质上是将实例恢复为 `PENDING`。已超过实例截止日期的记录不得撤回；无截止日期的普通任务不受“跨日”限制。
- 撤回前必须检查目标、项目和本周完成状态。已完成或已放弃的上层不得被任务撤回操作自动改变。

### 7.2 项目

项目状态：

```text
ACTIVE 进行中
COMPLETED 已完成
ABANDONED 已放弃
```

“待确认完成”是根据任务现状计算出的界面状态 `can_complete`，不是必须持久化的生命周期状态，避免任务变化后产生状态不同步。

项目自动进入待确认完成需要同时满足：

1. 不存在未完成或逾期的普通任务；
2. 不存在未来仍会产生实例的循环任务；
3. 所有已产生的循环任务实例均已完成或取消；
4. 至少有一个普通任务或循环实例实际完成。

项目不能自动完成。用户必须点击“确认完成”。

如果全部任务都被取消，项目不能确认为完成，只能继续补充任务或标记为已放弃。

### 7.3 目标

目标持久化状态与项目相同：

```text
ACTIVE 进行中
COMPLETED 已完成
ABANDONED 已放弃
```

目标的“待确认完成”同样通过 `can_complete` 实时计算。

目标自动进入待确认完成需要同时满足：

1. 所有未放弃的项目都已经确认完成；
2. 所有直接普通任务均已完成或取消；
3. 所有直接循环任务已经结束，不会再产生未来实例；
4. 直接循环任务的已有实例均已完成或取消；
5. 至少存在一个已完成项目、已完成直接任务或已完成循环实例。

目标不能自动完成。用户必须点击“确认完成”。

如果所有项目都已放弃且所有直接任务都已取消，目标不能确认为完成，只能继续补充内容或标记为已放弃。

### 7.4 放弃

放弃表达“该目标或项目不再继续”，不是完成。

- 放弃项目时，必须确认如何处理未完成任务和循环任务；完成放弃操作后不得留下活动任务。
- 放弃目标时，需要同时放弃仍在进行的项目，并取消目标下仍未完成的直接任务。
- 放弃操作必须二次确认。
- 放弃操作应可恢复；恢复后原先自动取消的内容默认仍保持取消，由用户选择需要重新打开的任务。

当前版本的放弃操作会撤下循环任务的未来待办、取消其已发生的待办实例，并取消所属普通任务的待办实例；历史完成记录保留。恢复目标或项目后，任务不会自动重新激活，需要在实例记录中逐项重新打开，循环规则可单独恢复。

### 7.5 重新打开与锁定

- 已完成的项目和目标默认锁定结构性修改。
- 在已完成项目中新增任务前，必须先重新打开项目；若目标也已完成，必须先手动重新打开目标，项目操作不得顺带改变目标状态。
- 重新打开已完成或已取消的任务实例时，所属目标和项目都必须已处于“进行中”；若仍是“已完成”，提示先手动重新打开，不能通过确认弹窗或 API 参数绕过。
- 在已放弃项目或目标中重新打开任务前，必须先恢复对应的上层事项。
- 按周循环若已确认“本周完成”，撤回同周的“今日完成／今日跳过”前，须先手动撤回“本周完成”；两个操作互不隐式撤销。
- 在当前周撤回“本周完成”时，仅从撤回当天起恢复本周尚未过去的提醒；此前处于“本周已完成”状态的日期不补造逾期。确认本周完成之前已存在的逾期照常保留。
- 目标和项目必须在卡片标题附近常显状态标识：`进行中`、`已完成`、`已放弃`。`待确认完成`是另一个准备就绪提示，不取代`进行中`状态标识。
- 不允许任务操作隐式改变已经确认完成的项目或目标。

## 8. 页面信息架构

系统包含三个一级入口：

1. 今日任务；
2. 近期任务；
3. 总事项安排。

### 8.1 今日任务

今日页面建议按以下顺序展示：

```text
待确认
边界风险
已逾期
今日截止
今日循环
已处理
```

#### 待确认

展示已经满足条件、等待用户确认完成的项目和目标。待确认项目和目标不是任务，不计入今日任务红色角标。

#### 边界风险

当目标或项目今天到达自身截止日期，但仍包含没有自身截止日期的未完成任务时，展示聚合风险卡，例如“目标今天截止，仍有 8 个无日期任务”。这些子任务不会被自动改成今天截止，也不逐条计入今日任务角标。

#### 已逾期

包括：

- 自身截止日期早于今天且仍未完成的普通任务；
- 实例截止日期早于今天且仍未完成的循环任务实例。

循环任务逾期实例不会因进入下一天自动跳过；达到单条规则 16 条上限时，仅自动清理最早的未处理逾期。普通任务逾期不会自动清理，可改期到今天或以后，或者手动删除。改期后原逾期从列表移出，按新日期进入今日任务、近期任务或总事项安排。循环逾期实例仅允许删除本条，不允许改期；所有逾期都不能事后标记完成或跳过。

#### 今日截止

展示自身截止日期等于今天且尚未完成的普通任务。

#### 今日循环

展示循环规则在今天命中的任务实例。按周循环在命中周的每一天显示，直至“本周完成”；“今日完成”或“今日跳过”只处理当天。按日循环即使实例周期超过一天，也在发生当天出现在今日循环中。

同一个实例同时满足“今日循环”和“今日截止”时只展示一次、只计数一次，优先归入“今日循环”。

#### 今日操作区

- 待处理的今日任务使用卡片左侧选择框执行`今日完成`。按周循环在同一操作区并列展示`今日跳过`和`本周完成`，两个入口同层级可见，不把跳过藏入“三个点”。
- 按日循环保留选择框与`今日跳过`；普通任务保留选择框与`取消任务`。三点菜单仅保留编辑、停止循环、删除等管理操作。
- PC 与移动端都要有可见的按钮边框／背景、悬停或按下反馈、键盘焦点态，点击区域高度至少 44px。窄屏可在同一操作区内换行，但不得折叠成菜单。
- `本周完成`停止本周剩余提醒，不清理此前逾期。它是周级操作，不等同于今日完成。
- `今日完成`和`今日跳过`不会禁用`本周完成`；用户可以先处理今天，再决定是否完成本周。直接点击`本周完成`也合法，不要求先完成今天。
- 点击`本周完成`时的确认说明要写清：本周剩余日期不再提醒、今日不会自动计为完成、历史逾期不变，并告知可在“已处理”撤回。周级成果可作为上层“已有真实完成成果”的依据，但与每日完成次数分开统计。

#### 已处理

“已处理”分成两个清晰的子组：

- **本周循环**：单独列出今日已完成或跳过的按周循环任务，以及当前周已标记“本周完成”的任务；该组有内容时常显，不藏进默认折叠的列表。今日已处理但本周未完成的卡片继续展示`本周完成`按钮；本周已完成的卡片改为状态`本周已完成`与`撤回本周完成`按钮。
- **其他已处理**：普通任务和按日循环任务，完成或跳过后展示状态及`撤回今日操作`；处理成功后自动展开，之后可由用户自行折叠。

同一按周循环任务在“本周循环”子组只显示一张卡片。若今天已完成／跳过且本周也完成，卡片同时标出两个独立结果；先撤回本周完成才能撤回今日操作。直接点击本周完成时，即使今日待办实例被撤下，也必须根据周完成记录显示这张卡片和撤回入口；不能只靠今日实例列表生成已处理区。本周结束后，当前周卡片退出今日页面，历史记录仍留在总事项安排。

不使用 10 秒或其他倒计时的撤回提示，也不依赖自动消失的通知提供唯一入口。撤回入口在允许撤回的期间持续可见；过期或被上层状态锁定时，显示明确原因和前往相应目标／项目的入口，而不是悄悄隐藏。今日操作过了实例截止日期后不再能撤回，逾期规则保持不变。

普通任务仅仅已经开始、但今天不是截止日期时，不进入今日任务。

### 8.2 今日红色角标

```text
红色角标 = 未完成逾期任务数 + 今日未完成任务数
```

- 已取消任务不计数；
- 同一任务或实例不重复计数；
- 超过 99 显示 `99+`；
- 待确认项目和目标不计入角标。

### 8.3 近期任务

近期范围支持用户选择：

- 7 天；
- 14 天，默认值；
- 30 天；
- 自定义天数。

近期窗口从明天开始，不包含今天：

```text
[明天, 今天 + N天]
```

展示自身截止日期落在窗口内的未完成普通任务。循环任务只在今日和总事项安排中展示，不占用近期列表及黄色角标。

不展示：

- 今日任务；
- 已逾期任务；
- 已完成或已取消任务；
- 项目和目标。

近期页面按日期分组，并允许按领域、目标和项目筛选。普通任务的上层时间边界不作为任务自己的近期截止日期。

### 8.4 近期黄色角标

黄色角标统计近期窗口内尚未完成的普通任务，不包含循环、今日及逾期任务。超过 99 显示 `99+`。

### 8.5 总事项安排

总事项安排是事项创建、组织和全局检查入口，以领域分组并呈现完整层级：

```text
健康
└── 完成半程马拉松       3.00月   12月20日
    ├── 购买跑鞋          1日      10月03日
    └── 准备上海半马      2.00周   10月31日
        ├── 选择训练计划   2日      10月05日
        └── 每周一三五跑步 循环     跟随项目
```

每一项至少展示：

- 名称；
- 类型；
- 状态；
- 开始日期；
- 周期；
- 自身截止日期和上层最晚允许日期；
- 循环标识；
- 逾期或时间冲突提示。

总事项安排提供“未安排截止日期”和“长期未更新”筛选，避免普通无日期任务长期沉底。父级最晚允许日期单独显示为边界提示，不冒充任务截止日期。

第一版以层级列表为主，时间轴或甘特图作为后续能力。

## 9. 响应式界面

### 9.1 PC 端

- 左侧固定一级菜单，显示红色和黄色角标；
- 当前一级菜单写入页面地址，刷新或浏览器前进、后退后保持对应视图；
- 中间为主要任务或层级列表；
- 点击事项后在右侧详情面板查看和编辑；
- 总事项安排支持逐层展开、收起和筛选；
- 批量操作使用列表选择模式。

### 9.2 移动端

- 底部使用三个主导航：今日、近期、总安排；
- 红色和黄色角标显示在对应底部导航上；
- 总事项安排使用可展开卡片，不直接缩放 PC 树形表格；
- 新增和编辑使用全屏表单或底部抽屉；
- 高频操作“完成”和“取消”在单手区域内可触达；
- 批量取消等高风险操作必须进入确认页，不使用容易误触的滑动手势直接执行。

建议在约 768px 宽度切换移动与桌面导航，但最终断点应根据实际组件测试确定。

## 10. 核心交互

### 10.1 新建事项

新建入口根据当前上下文预填所属层级：

- 领域卡片显示独立的“目标”按钮，点击后预选该领域；
- 目标展开区显示“添加项目”和“添加任务”，点击后预选该目标；
- 项目展开区显示“添加任务”，点击后预选该项目及所属目标；
- 在今日或近期页面新建任务时，必须选择目标，项目可选。

右上角“新建事项”保留为跨层级的全局入口；各级“三个点”仅放编辑、状态和删除等管理操作，不承担新增下级事项。已完成或已放弃的目标、项目须先重新打开或恢复，才显示对应的就地添加按钮。

表单应先展示必要字段：名称、所属关系、开始日期、周期或截止日期、是否循环。高级循环规则按需展开。

### 10.2 完成任务

- 普通任务点击完成后立即更新状态；
- 循环任务只完成当前实例；
- 完成最后一个阻塞项后，系统生成项目或目标待确认提示；
- 今日完成和今日跳过均可从“已处理”持续撤回，不显示限时撤回提示；其他页面的实例记录也应提供相同的撤回校验。
- 若目标／项目已完成或已放弃，先手动重新打开／恢复相应上层，任务操作不得自动改变上层状态；若按周循环已标记本周完成，还须先撤回本周完成。

### 10.3 取消任务

- 普通任务的按钮写作“取消任务”，取消后保留在历史中，与删除任务不同；
- 循环实例取消只影响本次；
- 取消不计入完成统计；
- 取消最后一个未处理任务后，如果上层至少有真实完成成果，上层可以进入待确认；
- 如果全部任务都被取消，上层只能放弃，不能确认完成。

### 10.4 确认项目或目标完成

确认对话框展示：

- 实际完成任务数；
- 已取消任务数；
- 开始和完成日期；
- 是否存在尚未解决的警告。

确认成功后锁定结构性修改，并记录确认时间。

## 12. 关键领域服务

实现时应将以下逻辑集中在领域服务中，避免分散到页面组件：

### 12.1 DurationCalculator

- 日、周、月转整数天；
- 保留原始周期值和展示单位；
- 开始日期与周期计算截止日期；
- 开始和截止日期反算周期；
- 格式化周和月的小数展示。

### 12.2 EffectiveDateResolver

- 计算最早和最晚允许日期；
- 检测父子日期冲突；
- 评估修改上层日期的影响范围。

### 12.3 RecurrenceService

- 判断某日是否命中循环规则；
- 幂等生成任务实例；
- 根据生成游标回填遗漏的历史实例；
- 计算循环最晚允许日期；
- 停止或取消循环；
- 聚合逾期实例。

### 12.4 CompletionPolicy

- 判断项目和目标是否满足待确认条件；
- 区分完成、取消和放弃；
- 撤回任务前校验截止日期、项目／目标状态及本周完成标记，不隐式回退上层状态；
- 禁止没有真实完成成果的上层事项确认完成。

### 12.5 TaskQueryService

- 查询今日截止；
- 查询今日循环；
- 查询逾期；
- 查询近期窗口；
- 查询无日期任务和父级边界风险；
- 去重并计算菜单角标。

## 13. 删除与历史数据

- 业务实体默认使用软删除。
- 完成记录和取消记录不能因停止循环而被删除。
- 删除循环任务时必须说明是否仅隐藏定义，还是同时软删除历史实例。
- 当前版本的“删除任务”是软删除任务定义，历史实例仍保留在数据库中，但该任务及全部实例都会从界面隐藏；确认弹窗必须说明影响范围。领域、目标、项目和任务均可在回收站恢复，恢复前校验上级状态与时间边界。
- 领域、目标或项目存在下级内容时，删除操作必须展示影响范围。
- 已完成事项优先归档，不建议直接删除。

## 14. 边界情况

### 14.1 没有截止日期

- 事项仍然可以存在于总事项安排。
- 普通任务不会因为开始日期到达而进入今日或近期。
- 循环任务根据循环规则进入今日，不进入近期。
- 上层截止日期只作为最晚允许边界，不自动变成普通任务的自身截止日期。

### 14.2 无限循环任务

- 不批量生成未来所有实例。
- 会阻止所属项目或目标完成。
- 可以通过设置结束日期、停止循环或取消循环任务解除阻塞。

### 14.3 大量循环逾期

- 每天错过的循环实例成为独立逾期记录，不因换天、换周或本周完成而消失。
- 每条循环规则最多保留最近 16 条未处理逾期；第 17 条出现时自动清理最早一条，并累计自动清理数量。
- 用户可以逐条删除循环逾期实例；逾期记录不能补标完成、跳过或重新打开。
- 普通任务的逾期不受此上限影响，不自动清理。

### 14.4 全部任务取消

- 项目或目标不能确认完成。
- 用户可以新增任务继续执行，或将项目、目标标记为已放弃。

### 14.5 跨时区

- 今日、逾期和循环命中都以用户设置的时区计算。
- 修改时区不会修改日期字段本身，但可能改变当前“今天”的判定。

### 14.6 并发操作

- 完成、取消和确认完成操作应具备幂等性。
- 确认项目或目标完成前必须在服务端重新校验条件。
- 前端显示可确认不代表服务端可以跳过最终校验。

## 15. 第一版验收标准

### 15.1 时间

- [ ] 新建事项开始日期默认为今天或允许的最早日期。
- [ ] 日只允许正整数。
- [ ] 周和月允许小数，换算后向上取整为整数天。
- [ ] 1.5 周归一为 11 天。
- [ ] 归一后仍保留用户输入的 1.5 周，不自动显示成 1.57 周。
- [ ] 1.5 月归一为 45 天。
- [ ] 修改开始日期、周期、截止日期时按既定规则联动。
- [ ] 子级不能保存到父级最早、最晚允许边界之外。
- [ ] 未设置自身截止日期的子级正确继承上层约束。

### 15.2 任务列表

- [ ] 今日页面只展示逾期、今日截止或今日命中的循环任务。
- [ ] 单纯已经开始的普通任务不会进入今日页面。
- [ ] 循环任务最多保留最近 16 条逾期；普通任务逾期不会自动清理。
- [ ] 近期默认展示未来 14 天且不包含今天。
- [ ] 红色和黄色角标不存在重复计数。
- [ ] 已取消任务不计入角标。

### 15.3 循环

- [ ] 无限循环不会预生成无限数据。
- [ ] 系统长时间未运行后，能够根据生成游标补齐遗漏实例。
- [ ] 同一循环任务同一天不会产生重复实例。
- [ ] 上层存在截止日期时，下层循环不会越过最晚允许日期。
- [ ] 停止循环不会删除已有逾期实例。
- [ ] 普通逾期任务可重设为今天或以后的截止日期并保持待处理，或手动删除；循环逾期只能删除本条；逾期不能补标完成或跳过，循环上限触发时仅清理最早记录。

### 15.4 完成状态

- [ ] 只有任务或任务实例可以直接完成。
- [ ] 满足条件的项目和目标进入待确认，而不是自动完成。
- [ ] 无限循环任务阻止上层进入待确认。
- [ ] 已取消任务不阻塞上层，但不计入完成成果。
- [ ] 全部任务取消时，上层不能确认完成。
- [ ] 目标和项目在卡片上常显进行中／已完成／已放弃；待确认完成作为独立提示。
- [ ] 已完成目标或项目阻止任务撤回；用户按目标、项目、任务的顺序手动重新打开后才可撤回，API 也不能绕过。
- [ ] 重新打开项目不会自动重新打开目标。
- [ ] 本周完成后，今日操作的撤回要求先撤回本周完成；撤回本周完成后从当天恢复提醒，不回填此前被周完成覆盖的日期或逾期，原有逾期保留。
- [ ] 按周循环的三个今日操作同层级可见且有明确按钮态；手机端点击区域至少 44px。
- [ ] 今日完成／跳过后，按周循环在“本周循环”子组仍可点击本周完成；直接本周完成不计入今日完成，但计入一项周级成果。
- [ ] 当前周已完成卡片即使没有今日实例，也会在独立子组显示撤回入口；同一任务不重复成两张卡片。
- [ ] “已处理”持续提供撤回入口，不依赖 10 秒或其他限时提示；过期和上层锁定时显示原因。
- [ ] 已完成上层在修改结构前需要重新打开。

### 15.5 响应式体验

- [ ] PC 使用左侧导航，移动端使用底部三项导航。
- [ ] 两种布局均能看到今日红色和近期黄色角标。
- [ ] 移动端总事项安排使用可展开卡片，不出现不可用的横向树表。
- [ ] 完成、取消和查看详情可以在移动端单手完成。

## 18. 公网访问安全

第一版面向单人使用，公网部署采用一个服务器端共享访问 Token，不引入用户账号体系。

1. `ACCESS_TOKEN` 和 `SESSION_SECRET` 只能配置为服务器密钥，不进入前端代码、URL、日志或 Git。
2. 登录时通过 HTTPS POST 提交 Token；服务端验证成功后签发 7 天有效的 HMAC 会话。
3. 公网会话 Cookie 必须使用 `Secure`、`HttpOnly`、`SameSite=Strict`、`Path=/` 和 `__Host-` 前缀。
4. 页面服务端渲染和全部业务 API 默认拒绝未认证请求，不能只在前端隐藏按钮。
5. 所有写请求除验证会话外，还必须验证同源 `Origin`，避免跨站请求伪造。
6. 退出登录清除会话；轮换 `SESSION_SECRET` 可以立即作废全部现有会话。
7. 公网入口必须强制 HTTPS、启用 HSTS，并对登录接口设置请求频率限制。
8. 数据库不直接暴露到公网，并建立独立于应用实例的定期备份。

单一 Token 无法区分设备或记录个人审计。未来若需要多人协作、逐设备吊销或权限分级，应升级为用户身份、独立会话和服务端授权模型，不能继续共享同一个 Token。
